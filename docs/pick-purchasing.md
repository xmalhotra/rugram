# Prices, offers and buy links

New product submissions require an explicit variant/pack description and one to five seller listings. Admin publishes directly; creator submissions retain admin moderation. Every seller record includes its own HTTPS buy link, seller name, listed INR item price, known shipping charge or `null` for unknown, delivery/stock/location note, and a submitter-reported check date. Optional offers require both a description and eligibility/conditions, with optional code, expiry and commercial/affiliate disclosure.

Native flow: Admin/Studio → Add/Submit product → product details → exact variant → seller details → optional offer. Enter another seller only when it is the same product/variant. The app does not inspect the seller page or prove variant matches automatically; moderation must verify these assertions. Price-check dates are not fabricated automatically from publication time. Date-only offer expiry currently means the end of the stated UTC day and is labelled accordingly in the form.

The API validates bounded entries, public HTTPS URL shape, no credentials or IP-address destinations, nonnegative finite prices/charges, nonfuture check dates, duplicate URLs and offer conditions. It derives the root listing price/URL/check date from the lowest listed item price; it never subtracts conditional offers. This summary remains compatible with budget filters and flow links. Unknown shipping is not free. A seller's complete checkout total, stock and delivery eligibility are not guaranteed.

Pick details prioritize seller prices, offer terms and external Buy buttons, followed by explanatory content and creator sources. Store labels use parsed hostnames rather than seller-provided marketplace branding. Recognized marketplace hosts have readable names; other stores show their real hostname. These are browser buy links, not Amazon/Flipkart/quick-commerce API integrations, embedded checkout, stock syncing, best-price guarantees or price monitoring. Store redirects and inventory must be checked with the retailer. This increment does not add automated tracking or collect the user's postcode.

Expired offers remain visibly marked expired, with no active coupon prompt. Unknown-expiry offers are explicitly unconfirmed. No savings score, bank-discount effective price, or order conversion is inferred. The existing creator-backing source remains distinct from a commercial disclosure or a price reference.

Data is stored in the existing product JSON within `mobile_catalog`; no database migration is required. Existing legacy products are readable and labelled incomplete rather than inventing seller offers. Canonical source-linked seed products receive one listing with their previously checked price and URL, no invented offer and unknown delivery cost; the pack/size caveats are retained. Demo hot reload enriches only records whose price, URL and check date still match the canonical source, preserving user edits and moderation. Database seeding inserts absent records only; existing database rows need a reviewed refresh. Product-editing and automatic price/offer refresh are not implemented here.

Tests cover URL handling, required fields, bounds, duplicate links, unknown/free shipping, expired/unknown-expiry offers, canonical price derivation and draft date parsing. The isolated function simulation checks seller and offer metadata through moderation/bootstrap; API integration testing uses a clearly labelled temporary fixture, not a real promotion. Native bundle compilation does not replace device accessibility and UI testing.
